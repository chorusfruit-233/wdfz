# 渲染效率测试

打开游戏设置，在「画面」下选择「对比 WebGPU / WebGL 效率（新标签页）」，或通过本地 HTTP 服务打开 `/benchmark/`。例如在仓库根目录运行 `python -m http.server 8000` 后访问 `http://localhost:8000/benchmark/`。WebGPU 需要浏览器支持及 HTTPS／localhost。

选择画质、测试画面尺寸、每场景采样时间和轮次，点击「开始对比」。默认均衡档、960×540、每场景 5 秒、两轮，依次测试教室、真实楼梯、室外校园。可以取消不需要的场景；手机也可操作，预览会等比例缩小，内部测试尺寸保持选定值。

## 比较口径

测试使用游戏原有 Three.js 场景、模型包、灯光、后期及设备选择逻辑。每个后端／轮次创建一个新的测试框架，场景顺序固定，随机源、日期、时间、SAN、镜头及画面时刻固定，冻结剧情、巡察、随机异象和背景粒子运动，不运行 HUD、声音和模拟更新。测到的是固定游戏画面的渲染负载，不是完整游玩的帧耗时。

为避免 WebGL 的显示画布默认 MSAA 与 WebGPU 无 MSAA 混比，测试框架统一关闭显示画布抗锯齿；这项覆盖仅作用于测试框架的 WebGL 上下文创建，正式游戏不变。场景渲染目标的 MSAA 仍按游戏画质设置，实际画布采样数和抗锯齿属性也参与可比性检查。

采样前先分别预检后端可用性，以流畅档初始化设备和驱动，再在正式轮次切到选定画质；避免把高画质资源构建混入设备启动。模型、字体加载和场景／后期的异步编译都在计时之外完成，两种后端均等待编译结果。每个场景还预热 2 秒、至少 3 帧，再开始采样。默认两轮顺序为 WebGL → WebGPU、WebGPU → WebGL，减少先后顺序的影响；四轮继续交替。每个采样段至少 3 帧，低速设备的实际耗时可能超过所选秒数。

| 指标 | 测量方式与含义 |
| --- | --- |
| 完成均值 | 从 `Engine.draw()` 调用开始，到本帧提交的工作完成；WebGL 用 `gl.finish()`，WebGPU 用 `device.queue.onSubmittedWorkDone()`。包含 CPU、GPU 和完成同步开销，越低越好。 |
| P95 | 完成耗时的第 95 百分位，使用排序后线性插值；反映慢帧。 |
| 提交均值 | JavaScript 渲染调用返回所需时间。WebGPU 异步提交，不应只用这列判优。 |
| 采样帧率 | 相邻采样帧起点之间的实际频率；包含浏览器帧调度和同步等待，可能受显示刷新率限制。它不是 `1000 / 完成均值`，也不代表正常游戏 FPS。 |
| 绘制次数 | 使用游戏 `Engine.metrics()` 的实际绘制调用计数，含后期；不是三角形数量。 |
| 几何／纹理计数 | 原始报告中的引擎资源对象数；不等于 GPU 内存字节数。 |

这是一项**逐帧等待完成的同步测试**。同步会改变通常的 CPU/GPU 并行流水线；结果不是纯 GPU 时间、峰值吞吐量、耗电或温度，也不能直接推算正式游戏的 FPS 提升比例。页面分别显示提交、完成及帧调度数据，不把异步提交耗时误称为 GPU 渲染耗时。

## 何时不给出判优结论

只有两种后端在所选每轮、每场景都成功完成，实际画布／内部渲染尺寸、DPR、MSAA、场景指纹和相机一致，各后端累计至少 30 帧且计时非零时，才显示该场景的完成均值差异。没有跨场景综合分，也不会自动修改游戏设置。

同档位仍可能使用不同的实际渲染规格，例如 WebGL 支持 8×MSAA 而 WebGPU 使用 4×。页面显示实际尺寸和采样数；不一致时保留数据但不判优。可以选择均衡档等无 MSAA 的档位再试。

如果浏览器没有 WebGPU，或申请设备后实际回退 WebGL，该轮标为「WebGPU 不可用」，不会把回退结果当作 WebGPU 成绩。采样过程中设备丢失、后端改变、上下文丢失、场景／分辨率改变或脚本报错，会丢弃当前未完成的场景数据并说明错误。

切到后台或点击「停止」会取消测试；已完整结束的场景可以导出，但不完整轮次不参加判优。测试框架和已创建的设备会释放。DPR 改变也会取消当前测试。

## 存档隔离与报告

测试页读取同源 `index.html`，在独立 `srcdoc` 框架中按原加载顺序执行游戏代码。框架在任何游戏脚本运行前，将自己的 `localStorage` 和 `sessionStorage` 替换为内存存储，再写入测试设置。普通存档、速通槽位、成就、上传 Mod、上一局痕迹和游戏偏好都不会被测试读取或覆盖。父页面也不保存结果到站点存储。

「导出 JSON」保存配置、实际后端、轮次／场景、实际画布和目标尺寸、MSAA、固定机位、场景指纹、适配器描述、每一帧的时间与绘制次数，以及完成／中断状态。报告方法版本为 `synchronized-render-completion-v1`。`source.indexFingerprint` 只标识所读取的 HTML，不是全部游戏资源的代码摘要；跨版本比较时另行保留仓库提交版本。

软件设备会在页面及报告标记，如 SwiftShader、llvmpipe。软件 GPU 的数据可验证流程，不能用来判断真实显卡的性能。比较实体设备时，使用同一浏览器版本、驱动、画质和尺寸，保持前台，关闭其他重负载程序，使用相同供电条件；可增加轮次并保留各次原始报告。测试不会上传报告。

## 实现与验证

- `benchmark/core.js`：纯配置、交替调度、统计和可比性规则，可在 Node 直接加载。
- `benchmark/runner.js`：仅在测试框架中加载；内存存储、固定场景、编译／预热、真实后端同步、取消和设备释放。
- `benchmark/page.js`：独立协调器、可见预览、结果、报告导出与后台取消。
- 正常游戏只增加设置页链接；引擎、玩法、模块清单和存档格式没有改动。

```bash
python tools/check_modules.py
PYTHONPATH=tests python -m unittest -v test_renderer_benchmark
```

专项覆盖统计定义、AB／BA 顺序、规格与轮次不足拒绝判优、WebGPU 不可用、存档／设置／会话隔离、停止、后台取消、移动端布局，以及真实 WebGPU 与 WebGL 在流畅档跑完三个场景的两轮对比，以及超精细／真实档的实际规格与回退标识。CI 加入相同专项，仅检查流程和数据正确性，不设置 FPS 或耗时达标线。

本地自动验证使用 Linux Chromium + SwiftShader，不能据此宣布实体 GPU 哪种后端更快。实体设备应运行此页面取得自己的结果。
