# 3D 代码审查报告：构建方式、生成逻辑与渲染引擎

审查对象是仓库里 3D 版的全部代码（`index.html` + `game3d/`），不含 2D 版。本文先说现状和问题，再说这次改了什么、为什么这样选引擎，最后列出还没做的。

审查时的规模：48 个脚本、约 1.25 万行 JavaScript、685 个顶层全局函数和变量；three.js r160（全局构建），不加载任何外部资源，双击 `index.html`（`file://`）离线可玩。

## 一、现状

### 1. 加载与构建

- `index.html` 里手写 48 个 `<script>`，靠先后顺序保证依赖；没有打包、没有模块系统，全部是全局变量。
- 好处是简单、离线可玩、改一个文件刷新就生效；坏处是：
  - 加一个文件要找对位置插进去，顺序错了就是一片 `undefined`，而且不会报在出错的地方；
  - 哪些文件是一组的、哪些可以按需加载，看不出来；
  - 一个 7 MB 的库（比如第二个引擎）要么所有人都加载，要么另写一套加载逻辑。

### 2. 生成逻辑

整个场景都是程序生成的，没有模型文件：

| 层 | 文件 | 做法 |
| --- | --- | --- |
| 地图数据 | `map.js` | 每层楼一张字符网格（`#` 墙、`d` 课桌、`S` 楼梯……），室外是一张矩形列表 `OBJ` |
| 建模工具 | `model/kit.js` | 盒、倒角盒、圆柱、杆、椭球、四边形，按材质分组合并成少数几个网格 |
| 家具 | `model/furniture.js` | 每个字符一个建模函数 `FURN[ch]` |
| 房间 | `model/room.js` | 地面、合并后的墙、踢脚线、门、楼梯、窗，再逐格调用家具 |
| 楼与室外 | `model/building.js`、`model/outdoor.js` | 每栋楼一个函数，室外道具按段落生成 |
| 碰撞 | `world.js` | 网格字符 + 每种字符一个固定比例的方块（`FURN_SOLID`） |
| 巡察者 | `patrol.js` | 1 米格子上找路，走格子中心 |

### 3. 渲染

- `render.js` 建 three.js 渲染器、离屏缓冲和一段后期着色器（色调、暗角、SAN 抖动、受伤、红光……）。
- 每帧：场景画进离屏缓冲 → 后期画到屏幕。这几行直接写在 `main.js` 的 `render()` 里。
- 手里的手电、伞、手机挂在相机上，和场景一起画。

## 二、发现的问题

### A. 建模和碰撞对不上（穿模的根源）

1. **碰撞是「按字符的固定方块」，和模型无关**。课桌模型比方块大 5 厘米、自己的座位根本没有碰撞、行政楼的大办公桌和柜子比方块大 18 厘米，人能走进去。
2. **建模时不知道周围有什么**。例子：
   - 楼梯两侧的挡墙不管旁边是不是墙，一律立起来，贴着外墙时戳穿墙上的门框；
   - 窗户只看正下方那一格是不是楼梯，1.5 米宽的窗会被旁边的楼梯梁插进去；
   - 外墙的窗、墙基、腰线不知道门在哪、旁边贴着哪栋楼。
3. **尺寸写成比例**。女儿墙压顶按「楼宽 × 1.02」挑出，48 米宽的教学楼挑出近半米，插进旁边钟楼的柱子；墙基按「楼高 × 0.14」，宿舍的墙基 2.5 米高，一楼的窗整个埋在里面。
4. **巡察者走格子中心**，身体半径 0.28 米，会擦过办公椅、机房桌椅。

### B. 档位参数散落

「流畅 / 均衡 / 精细」的差别散在 10 个文件、18 处（`QUALITY===0 ? 14 : 24`、`[500,900,1500][QUALITY]`……），而且写法不一：有的是 `QUALITY>1`，有的是 `QUALITY===2`。加第四档时，`===2` 那几处会在第四档上悄悄退回均衡的效果。

### C. 渲染和游戏逻辑绑死

`main.js`、`shade.js`、`materials.js`、菜单拍照都直接调 `GLR.renderer`。想换引擎或加一种画法，要改游戏逻辑的文件。

### D. 其他

- 室外楼的分派是一长串 `if`；
- 手持物和场景一起画，贴墙时伸进墙里；
- 车库里那个人的碰撞只看脚下一个点；
- 地图上的错误没有检查：宿舍东南角那间的门被楼梯堵住，进不去；行政楼 3 楼的数据终端被两排工位夹住；花坛的判断条件写反了，会建在车库坡道上；体育场跑道压进篮球场。

## 三、这次的改动

### 1. 穿模：先做工具，再按报告逐项修

- 新工具 `tools/clip_audit.js`（+ `clip_audit.py` 批量跑、`clip_view.py` 给问题点拍照）。它在建模时记下每个图元的真实形状和归属，检查：
  - 互相插入（区分「正常安装」：踢脚线埋进墙、雨棚插进墙、篮球架底座压在场地上不算）；
  - 穿墙、伸进门洞；
  - 看得见的部分超出碰撞；
  - 巡察者擦碰；
  - 走不到（门全开时，门、出口、楼梯、座位、柜子、能搜的家具 1.2 米内要有能站的点）；
  - 坐着的同学和桌椅。
- 首轮报告：互相插入 934 处（其中室外 77 处）、看得见却没碰撞 906 处、巡察者擦碰 904 处；加上可达性检查后又查出走不到的门、终端各一处。现在全部为 **0**，并写进了回归测试，只降不升。
- 修法见[更新说明](3D更新说明.md)的「穿模修复」一节。

### 2. 碰撞改成「从模型来」

建房间时，建模工具顺手记下每件家具在人身高范围（0.10–1.85 米）内每个图元的水平外包矩形（`Kit._cap` → `R.foot`），碰撞直接用这些矩形。以后改模型，碰撞自动跟着变，不需要再手调 `FURN_SOLID`（它只在房间还没建模型时兜底）。

### 3. 巡察者细网格寻路

每格切成 4×4 个 0.25 米的小格，墙、楼梯、家具真实占地往外胀一个身体半径，胀进去的不能走；门实时判断；找到的路径再拉直（`patrol.js`）。

### 4. 画质档位表（`quality.js`）

四档的所有差别写在一张表 `QPROF` 里：引擎、像素比、离屏缩放、贴图尺寸、分段倍数、阴影、光柱、树草花数量、雨和蛾群数量、物理步进、碰撞方式、环境光遮蔽、抗锯齿、帧率下限。各处只问 `QP().xxx`。原来散落的 18 处全部改成查表。

### 5. 渲染层（`gfx/`）

游戏逻辑只管往 three.js 的场景图里摆东西、挪相机；每帧怎么画交给渲染层选中的后端：

```text
game3d/js/gfx/gfx.js              选后端、按需加载库、失败退回、窗口尺寸
game3d/js/gfx/three-backend.js    Three.js：离屏缓冲 → 手持物单独一遍 → 后期
game3d/js/gfx/babylon-backend.js  Babylon.js：把同一份场景图镜像进去画
```

`main.js` 里原来直接调渲染器的几行换成了 `GFX.frame()`。手持物移到单独的 `GLR.handScene`，清了深度再画，贴墙也不会插进墙里。

### 6. 脚本清单（`manifest.js`）

`index.html` 只引一个 `game3d/js/manifest.js`，加载顺序按模块分组写在里面（基础、建模、世界、特效、系统、渲染层、启动）；按需加载的大库登记在 `lazy` 里。用 `document.write` 插标签，执行方式和手写的 `<script>` 完全一样，`file://` 离线照样能玩，不需要打包。

### 7. 生成逻辑改成查表

- 室外：`BLD_BY_ID` / `BLD_BY_KIND` 两张表决定每个地图对象用哪个建模函数，取代原来那串 `if`。
- 外墙：`FAC` 记下正在建的楼和它的门，窗、墙基、腰线统一问 `facadeBlocked()`：门口那段、贴着别的楼和连廊的那段不开窗、腰线和墙基断开。
- 尺寸：女儿墙、墙基改成固定挑出量，不再按楼宽的百分比。

## 四、引擎选型

用户给的候选：Three.js、Babylon.js、PlayCanvas、Unity、Godot。

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| **Three.js** | 流畅、均衡、精细三档 | 现有代码就是它；最小（0.65 MB）；手机上最省 |
| **Babylon.js** | 超精细 | 自带屏幕空间环境光遮蔽（SSAO2）、PCF 软阴影、立方体阴影、FXAA；PBR 材质；和 Three.js 一样能用一个 `<script>` 离线加载（Apache-2.0，`game3d/lib/babylon.js`，7.9 MB，只在需要时加载） |
| PlayCanvas | 不用 | 引擎本体可以独立用，但它的长处在在线编辑器和资源管线；能给的画面特性 Babylon 都有，再写一个后端只多维护成本 |
| Unity / Godot | 不用 | 要把整个游戏导出成 WebAssembly：几十 MB、首屏慢、不能双击 `index.html` 离线玩，游戏逻辑（全是 JavaScript）要重写 |

**怎么做到「换引擎不重写游戏」**：Babylon 后端是「镜像」——每帧遍历 three.js 场景图，把网格、材质、灯、雾、相机同步进 Babylon 再画：

- 几何体：同一份只转换一次；雨丝、点云这类每帧在动的原地更新；
- 实例化网格 → thin instance；点 → 点云；线 → 线；精灵 → 永远朝向镜头的面片；
- 材质：不受光的 → PBR unlit；Lambert / Phong → PBR（高光强度换算粗糙度）；透明、叠加混合、不写深度、多边形偏移、双面照搬；
- 灯：环境光、天光 → 半球光；平行光、点光、聚光灯照搬，点光的衰减用「平方反比 + 距离窗口」，和 Three.js 一致；
- 相机直接用 three.js 的视图矩阵；
- 最后过同一段后期着色器（从 three.js 那段原样搬过去），所以色调、SAN 抖动、红光都一样。

**亮度校准**：用一块反照率 0.5 的平面、一盏灯，在两个引擎里分别读像素：

| 灯 | Three.js | Babylon PBR（线性输出） | 处理 |
| --- | --- | --- | --- |
| 环境光 / 天光 | 41 | 128 | Babylon 半球光不除 π，乘 1/π |
| 平行光 | 41 | 41 | 不用换算 |
| 点光（1 米、2 米） | 41 | 41 | 不用换算 |

两个坑：Babylon 的 PBR 在关掉图像处理时会先把输出转成 gamma，后期再转一次就整体发白，要让材质「线性输出」（`applyByPostProcess`，而且要给每个材质单独挂一份配置，场景那份会被环境光遮蔽的预渲染改掉）；两边对「正面」的绕序约定相反，要反过来剔除。

**同画面对比**（`tools/engine_compare.py`，800×450，软件渲染）：

| 画面 | Three.js 平均亮度 | Babylon.js 平均亮度 |
| --- | --- | --- |
| 开局座位上 | 116.9 | 117.3 |
| 教学楼外 | 53.8 | 55.2 |
| 行政楼 | 183.1 | 191.2 |
| 车库 | 15.9 | 13.8 |

截图见 `pictures/穿模与超精细/`。软件渲染下的毫秒数只能比相对快慢，不代表显卡上的帧率。

## 五、超精细档

- **光影**：Babylon.js 引擎；像素比到 2；环境光遮蔽；4096 软阴影（室外的太阳 / 月光）、2048 手电阴影、离镜头最近那盏顶灯的立方体阴影；FXAA。室内的月光直接关掉（Three.js 开着阴影时它本来就被天花板挡住）。
- **建模**：圆柱、杆、椭球分段 × 1.6；贴图 1024；树 240 棵、草 1.6 万丛、灌木 60 丛、花坛每个 21 朵；雨 2400 丝、蛾 180 只。
- **物理**：每帧切 4 小步（240 Hz），人当成半径 0.333 米的圆，和附近每一块实心矩形算最近距离，撞了分别沿 x、y 贴着滑；钟楼旋梯这种不是矩形的再沿圆周取 12 个点。以前四个探测点之间，家具的角能斜着戳进人身体 10 厘米。
- **镜头**：镜头在人中心；近裁剪面四个角离镜头最远 0.16 米，小于人的半径 0.333 米，所以镜头不会穿进墙（测试里验证这个关系）。
- **性能保护**：玩的时候帧率连续 8 秒低于这一档的下限（均衡 24、精细 28、超精细 30），问一次要不要降一档，可以选「别再问了」。

## 六、还没做的、建议以后做的

1. **模块化**：全局变量太多（685 个）。下一步可以按 `manifest.js` 的分组，逐组包成命名空间（`WDFZ.model.*`、`WDFZ.world.*`），先从没有外部引用的内部函数开始。
2. **室外碰撞也从模型来**：室外道具现在是手写的 `addSolidM`（审查里没有发现对不上的），可以照室内的做法从模型自动生成。
3. **建模内核**：已重写（类型化数组、压缩顶点、隐藏面剔除、切块、场景缓存、开门只换门扇），缓冲区少约 40%，见 [3D 更新说明](3D更新说明.md)「建模内核重写」。下一步可以把同一材质的重复家具改成实例化绘制，进一步减少绘制次数。
4. **Babylon 后端直接建模**：现在是镜像，每帧遍历场景图有开销（几百个对象，软件渲染下约 1–3 毫秒）。如果以后超精细档要再加东西（比如体积光），可以让建模工具直接输出 Babylon 网格。
5. **真机测试**：所有截图和帧率都来自无头浏览器的软件渲染，需要在独立显卡、核显、手机上各跑一次超精细，确认帧率和降档提示。
