# 项目解耦与模块化

> 当前衔接（2026-11-03）：在已有基础拆分上补齐文件依赖、主循环、空间配方、随机源和规则／表现收口；整体状态见[计划目录](README.md)，交付记录见第 12 节。此前第 10–11 节的代码与测试数字保留历史口径。

> 整体实施状态见[计划目录](README.md)。第 1–9 节定义目标、模块边界、迁移顺序与验收要求；实际交付以第 10 节和模块接口文档为准。

最初方案基于 2026-11-02 核对的 [PR #25](https://github.com/chorusfruit-233/wdfz/pull/25) 提交 [`55f7e23`](https://github.com/chorusfruit-233/wdfz/commit/55f7e230233eb81644daee84d170a20747ad776f)。当时 `main` 为 `6927431`。PR 中包含尚未进入主分支的天赋、开场、档案室等功能，最新执行指示为直接在 `main` 完成，不等待 PR。实施基线为 `6927431`，该基线尚无 PR #25 的新开场、速通、死亡档案室和天赋规则 2；这些能力的接口约束保留，实施与验收按主分支实际存在的功能展开，不合入未审查的 PR。

## 1. 目标与交付范围

项目已经有按功能拆分的文件、`Engine` / `VisualState`、异象注册表、存档字段表和天赋接口。本轮沿用这些成果，重点补齐状态归属、输入优先级、生命周期和依赖约束。

目标是让一次功能变更的影响范围可以明确说明，让新游戏、读档、场景切换、死亡、回放和调试退出走可验证的流程。交付以行为稳定和维护成本降低为准，不以文件数、目录层数或全局变量数量单独判定成败。

范围包括：

1. 统一游戏流程与输入分派，消除多个布尔标志共同决定同一行为的歧义。
2. 为游戏状态指定负责模块，收拢修改入口，明确真实时间、模拟时间、游戏日历和表现时间。
3. 统一场景、会话及演出的进入、退出、恢复和资源清理。
4. 分离规则判定与镜头、画面、音效，让调试预览和档案回放有独立的运行上下文。
5. 将存档适配、界面和调试工具接到明确接口，形成能持续检查的模块依赖边界。

本轮保持 Three.js，保留现有模型、关卡和玩法。异色空间重新设计、数值平衡调整、新玩法、引擎替换和联机功能不纳入本计划。模块接口可以为后续扩展留出位置，本轮不为尚未确定的功能建立复杂框架。

## 2. 现状与证据

以下统计只对应上述代码快照：`game3d/js/` 有 75 个 JS 文件，`index.html` 顺序加载这 75 个普通脚本；57 个文件引用全局状态 `S`，至少 28 个文件存在直接改写 `S` 顶层字段的赋值语句。后一个数字来自静态模式扫描，不包含所有嵌套字段和间接修改，也不等于完整依赖图。读取共享状态本身不是缺陷，重点是同一字段的写入责任和退出行为不清楚。

| 编号 | 当前证据 | 维护影响 | 本轮处理方向 |
| --- | --- | --- | --- |
| A-01 | `input.js` 在处理 `S.screen === 'cut'` 之前处理 `PRO.on`；`Opening.play()` 又会设置 `PRO.on` | 新开场的空格被旧 `proNext()` 接走。撤回异色空间前后均已复现，属于已知缺陷 | 为每种输入上下文指定唯一处理入口，修复开场跳过并保留回归 |
| A-02 | `main.js` 的 `freshState()`、`Game.quit()`，以及读档、调试传送等各自列出清理调用 | 加一个系统需要记得修改多条路径，容易留下定时器、镜头或事件状态 | 建立会话与场景生命周期，由系统声明自己的清理责任 |
| A-03 | `main.js` 的 `render()` 中检查 `solidAt()` 并调用 `unstick()` | 渲染更新会改变玩家位置，模拟暂停与渲染继续时的行为难以推理 | 把位置修正移到模拟或场景交接，验证暂停和各档画质一致性 |
| A-04 | `S`、`RT`、`AN`、`PAT`、`PRO`、`CUT`、`PAUSE` 等共同决定输入、存档与演出 | 同一流程需要跨多个模块了解标志组合 | 建立状态归属表和查询接口，逐步收拢对内部字段的写入 |
| A-05 | `SAVE_SCHEMA` 已集中字段，但部分恢复过程同时写入表现状态；`BrowserCase` 常通过整页加载设置全局状态 | 规则测试依赖浏览器环境，加载顺序和副作用增加排查成本 | 分开数据迁移、规则恢复、表现重建，补充脱离渲染的规则测试 |
| A-06 | 多处空 `catch` 把调用失败静默吞掉 | 生命周期或接口接错时可能表现为功能偶尔不工作 | 为关键边界记录带模块、阶段和会话信息的诊断，保留必要的可选效果降级 |

A-02 至 A-06 是结构性风险和改进依据，不代表每条路径都已发现运行故障。历史上的调试预览、传送和镜头问题应先核对现有修复，再转为长期回归，避免重复宣称旧问题仍存在。

## 3. 必须保持的产品约束

| 领域 | 重构约束 |
| --- | --- |
| 引擎与画质 | 保留 Three.js 和当前五档画质；游戏规则、碰撞与移动不因画质改变，资源继续本地提供 |
| 时间与难度 | 沿用 20 分钟自然日、探索与课程机制，以及尽量当天逃离、第二天起高危的留校升压规则；快进、跨日、倒退的现有结算边界逐一保留 |
| 天赋与存档 | 兼容已有存档字段及天赋规则版本；一次性能力、异象连续状态、巡察与电梯状态不能因迁移重置或重复奖励 |
| 操作 | 桌面鼠标捕获、触屏、混合输入、自定义触屏布局保持可用；调试面板打开且未主动暂停时，面板外仍可操作游戏 |
| 演出与进度 | 新局、死亡、保护、复活、回放、跳过、返回菜单各自只交接一次；预览与回放不解锁正式档案、不推进路线或写入当前游戏存档 |
| 速通 | 保留当前 RTA 的起终点、暂停和切后台继续计时、独立存档槽及成绩有效性规则；重构不得无故清空成绩 |
| 部署与离线 | 保留静态托管和离线资源启动能力；模块方案要验证现有启动方式，不能暗中增加 CDN 或线上构建服务依赖 |
| 信息披露 | 内部计划和测试可以涉及隐藏内容；玩家 Wiki、调试之外的常规界面不因重构泄露隐藏路线、触发条件和精确时刻 |

行为等价以输入、受控随机序列、时间步和存档一致时的游戏结果为依据。A-01 等明确缺陷单独记录修复前后预期，不把错误行为永久固化。其他玩法变化另列产品变更，不能夹在重构中顺带调整。

## 4. 目标模块边界

### 4.1 分层与依赖方向

| 层 | 负责内容 | 允许的依赖与禁止的越界 |
| --- | --- | --- |
| 应用流程 | 开局、继续、退出、主循环、模式切换、生命周期编排 | 组合规则和适配器；不在这里继续堆放每个异象、房间和物品的细节 |
| 游戏规则 | 玩家状态、时间与压力、物品、天赋、异象、巡察、课程、路线和结局判定 | 调用显式规则接口、查询地图数据；不依赖 DOM、Three.js、`GLR` 或浏览器存储 |
| 内容数据 | 异象、天赋、物品、房间与演出定义 | 复用现有注册表；配置与实例状态分离；程序化行为可以保留有名字的处理函数 |
| 表现 | 场景、模型、镜头、灯光、特效、音效和界面显示 | 消费只读规则视图和已发生事件；维护自己的资源与动画状态，不直接改变权威玩法状态 |
| 平台适配 | 键鼠与触屏原始输入、存储、浏览器时间、可见性、设备与资源加载 | 对上暴露明确接口；不自行判定通关、扣 SAN 或消耗道具 |
| 开发工具 | 调试窗口、诊断、测试控制与录像辅助 | 调用应用或规则命令；表现预览使用独立上下文；显式标记影响成绩的操作 |

规则模块之间按实际需求传入小接口，例如天赋修正、时钟查询和地图碰撞查询。不要传入包含所有系统的万能对象，把原来的全局依赖搬成另一种形式。跨系统通知仅用于“已经发生”的事实；需要立即获得判定结果的操作使用明确调用。

### 4.2 目录演进

以下是目标职责，不要求先进行整仓移动：

```text
game3d/js/
  app/           启动、会话、模式切换、生命周期与输入路由
  domain/        游戏规则及其状态、命令和查询
  content/       版本化规则定义与地图、物品、异象配置
  adapters/      浏览器输入、时钟、存储和资源适配
  engine/        保留现有 Three.js 封装，逐步收紧接口
  model/         保留模型与共享尺寸、碰撞描述
  fx/            演出与特效实例，不持有正式游戏写权限
  ui/            HUD、菜单与面板
  dev/           调试命令、预览和诊断
```

每迁移一个系统，先写清接口和归属，再移动有必要移动的文件。`AN_DEFS`、`SAVE_SCHEMA`、`Talent`、`Engine` 等已有机制继续复用；不为统一命名重写已稳定的逻辑。

## 5. 核心设计约定

### 5.1 游戏模式与输入归属

建立会话模式与界面覆盖层两级管理。会话模式描述菜单、加载、正常游玩、过场、死亡和回放；背包、选择、手机、课堂互动与调试面板作为各自的覆盖或局部交互上下文，不塞进一条巨大的互斥状态列表。

输入流程固定为：原始键鼠／触摸事件 → 规范化动作 → 按焦点与模式分派 → 当前上下文处理 → 未消费的动作交给下一允许上下文。

- 保留物理键位映射、鼠标锁定与触屏手势现有行为；同一次触摸补发的 click 不能重复执行操作。
- 打字时由输入框处理文字。非暂停调试面板只消费面板自身交互，面板外的游戏操作仍可继续；拖动与主动冻结分别声明输入限制。
- 开场、旧文字前情提要、结局演出和死亡演出各自拥有跳过或翻页动作。旧 `PRO.on` 在迁移期只能是兼容映射，不再同时充当多个流程的权威开关。
- 模式退出统一释放按键、指针捕获和手势状态；重新开始不能继承上一段移动输入。
- 模式转换返回成功或拒绝原因；同一次结束、跳过与超时回调只完成一次交接。

M0 应先列出实际输入优先级表；M1 用该表替换散落的判断，覆盖当前所有上下文，不能只修空格的一处顺序。

### 5.2 状态归属与命令

为持久化游戏数据、瞬时模拟状态、表现状态和界面状态分别建立归属表。玩家数值由对应规则模块维护，背包由物品模块维护，时钟与跨日由时间模块维护，异象与巡察维护自己的运行状态。

接口示例用于表达职责，最终名称可随现有代码调整：

- `PlayerStats.changeSan(amount, source)`：统一修正、上下限、结算顺序及原因记录；是否应用天赋和压力由调用语义明确区分，避免重复乘倍率。
- `Inventory.use(itemId, context)`：完成条件检查与一次性消耗，返回结果，界面再展示反馈。
- `GameTime.advance(minutes, reason)`：处理沿途时间边界和跨日通知；不能只改数字跳过检查。
- `Session.teleport(destination, policy)`：按传送语义完成事件处理、旧场景退出、位置校验和新场景重建。

正式游戏操作、存档恢复和调试设置分开入口。存档恢复不重放吃药、领奖等玩法副作用；调试直接设值仍进行范围校验和状态同步，并沿用成绩失效规则。

迁移期允许 `S`、`RT` 等兼容外观，但一个字段只保留一份权威数据。按字段逐步迁移写入者，未迁移调用通过适配层访问，禁止长期保留两份可独立修改的状态。只读视图按需生成或复用，不要求每帧深拷贝整个世界。

### 5.3 生命周期与异步操作

统一会话、场景、活动事件和演出的生命周期。系统按需要实现初始化、更新、进入／退出、序列化／恢复和释放钩子，不要求每个模块填满全部方法。

- 调度器持有明确的执行顺序和依赖表，先保持现有已验证顺序，再单独评审必要调整。
- 每个作用域登记自己的定时器、订阅、音源、DOM 监听和可释放渲染资源；退出时取消，重复退出应安全。
- 共享模型、纹理和音频缓存由资源管理模块拥有；局部演出退出只释放自身持有的资源，不能误释放仍被世界使用的共享资产。
- 使用会话或场景代号检查异步回调是否过期。上一局的加载完成、字幕超时和死亡回调不得修改下一局。
- 正常过门、读档、调试传送采用不同的事件策略：逐项保留现有“持续／取消／恢复”规则，不统一清空所有异象，也不让旧房间事件无条件泄漏到新房间。
- 新局、继续、返回菜单和调试复活从统一应用入口编排；各模块负责自身重置，入口不再手写它们的内部字段。

### 5.4 时钟和暂停语义

| 时钟 | 用途 | 约束 |
| --- | --- | --- |
| 模拟运行时间 | 移动、威胁、持续效果及按运行秒结算的事件 | 由固定步进驱动；暂停策略决定是否推进，渲染帧数不得改变结果 |
| 游戏日历时间 | 课表、检查、熄灯、跨日与校园压力 | 沿用 20 分钟自然日映射与现有特殊窗口；快进需要依序处理跨越边界 |
| 表现时间 | 镜头、字幕、渐变和特效 | 可以在模拟暂停时继续，但具体演出遵守自己的暂停策略；不能偷偷推进玩法判定 |
| 真实经过时间 | 速通 RTA、界面需要的真实时间测量 | 保留当前单调时钟与墙钟的补偿语义，暂停、后台和系统休眠按速通规则处理 |

M0 为菜单、开场、暂停菜单、背包／选择、手机／课堂、调试冻结、死亡、回放、异常电梯空间和后台状态建立完整矩阵，分别标注移动输入、模拟、日历、演出和 RTA 是否推进。矩阵先记录现状与已确认产品规则；遇到冲突列出具体差异，不能借统一时钟改变游玩节奏。

### 5.5 规则与表现分离

游戏规则产生伤害、死亡、事件开始／结束等结果；表现层根据结果播放音画，演出完成后只向应用流程报告完成或取消。游戏状态与镜头偏移分别保存，避免把临时镜头高度、朝向写回玩家权威位置。

- 将 `render()` 中的卡墙纠正移到固定模拟更新或场景进入后的定位校验；暂停时不靠渲染循环偷偷移动玩家。
- 画质切换只重建表现资源，沿用统一碰撞数据；规则查询不需要加载 Three.js 模型。
- 调试预览、档案回放和真实死亡共用演出定义，各自有独立实例、时间源、镜头和结束处理。演出不能通过隐式全局变量访问正式存档写入器。
- 同一对象的视觉插值、消失和资源销毁由表现模块负责；是否仍具有碰撞、是否伤害玩家由规则决定。
- 对规则真正依赖的演出节点，用显式完成通知和取消策略衔接，保证跳过与完整播放的业务结果一致。

### 5.6 存档恢复与兼容

保留 `SAVE_SCHEMA` 的集中入口，逐步让每个系统提供自己的数据序列化与校验。恢复顺序为：读取和校验 → 版本迁移 → 准备会话状态 → 按依赖恢复规则 → 重建表现 → 恢复允许的输入与运行。

- 纯代码搬移不强制改变磁盘格式；需要新增版本时提供明确迁移和旧字段默认值。
- 不持久化 Three.js 对象、DOM、浏览器定时器 ID、监听器或函数；恢复剩余时间及去重标记。
- 保留普通与速通存档槽、个人成绩及死亡档案各自边界；加载失败不覆盖原始存档。
- 旧字段兼容从唯一权威状态派生，不能同时作为独立数据继续修改。
- 读档不重新抽取已经确定的随机事件，不重复支付奖励、消耗物品或补充已使用的保命次数。
- 对当前依赖 `freshState()` 再覆盖字段的流程逐步迁移，先保证旧行为，再消除新局初始化的无关副作用。

### 5.7 模块加载、错误与诊断

初期继续支持普通脚本，用显式模块接口和统一启动入口改善依赖。M5 在实际启动约束下比较原生 ES Modules 与本地构建产物；优先保证静态站点、断网资源及需要保留的本地启动方式。若原生模块不能满足直接打开页面的要求，采用兼容构建产物或保留普通脚本，不把加载方式切换当作重构完成的必要条件。

关键规则、存档和生命周期异常必须能被测试捕获，并记录模块、操作阶段、会话标识和原始错误。可选音效、设备能力缺失等允许降级，但不能用空 `catch` 掩盖半恢复状态。调试面板增加输入当前归属、模式、各时钟是否推进和活动资源作用域的诊断；只在开发工具里展示实现细节。

### 7.2 性能与设备

- 同一设备、同一画质、相同场景和输入轨迹对照固定步耗时、帧耗时、绘制量、场景切换及连续重开后的资源变化。
- 输入路由和状态接口不能引入每帧全量 JSON 序列化、深拷贝或大量短命对象。性能异常须定位到具体改变，再决定修复或回退。
- 检查桌面鼠标捕获、触屏竖屏与横屏、混合输入、后台恢复和资源加载失败。触屏仿真不等于实体手机验收。

5. **随机流分离**：画面／声音不再消耗玩法来源；同学布局从已有本局种子稳定推导。由于旧版曾混用随机流，新旧版本在相同 `Math.random` 种子下不再逐次抽取相同结果；概率配置和已存事件连续状态不变。这个差异作为边界修复明确记录。
6. **接线与约束**：Mod API 保持 1.0，具体游戏服务由应用适配器注入。AST 检查覆盖词法依赖、别名写入、纯规则与配方边界，运行时只读视图阻止表现层修改权威状态。GitHub Actions 加入快速架构／纯规则检查；更新模型查看与几何审查工具的接线。

本轮覆盖的是架构边界及其自动约束。保留的跨系统调用均经过明确端口；不把“解耦”解释成没有业务交互，也不声称已经消除所有兼容全局或把所有带界面的控制器变成纯函数。旧数据格式、Three.js、五档画质、20 分钟自然日和现有路线规则继续保留。验收过程与证据见[彻底解耦验收](../validation/彻底解耦验收.md)。
