# 天赋系统重构

本计划基于 `main` 的 `23afa29207feaaea49c17cfb2a530a457220d50e`（2026-11-01）核对代码、文案、存档和浏览器行为。整体实施状态见[计划目录](README.md)。本次交付为分析与方案，下面的选择界面、新效果、迁移协议和验收门槛均未实施。

## 1. 结论与重构顺序

当前天赋能生效，但还没有形成完整的角色选择系统：新局随机分配，玩家主要在暂停时才知道自己获得了什么；六项能力分别影响路线门槛、区域消耗、单一异象、时钟和死亡保护，作用机会与收益不可直接比较；效果定义、判断和展示分散在多个模块。

优先处理三件事：

1. **让当前规则可信**：修复天赋文案、剩余次数、路线提示、无效存档和一次性效果落盘问题。
2. **让玩家能作出选择**：在新局开始前展示能力、限制与可选玩法，提供明确选择和随机入口；读档保持原选择。
3. **再验证玩法价值**：为只在极少情境下有用的能力补充有限、可感知的用途；对跳过准备步骤的能力增加明确取舍。所有新数值先作为试验配置，不能把自动化通过当成平衡已经成立。

不先扩充到十二项，不加入天赋树、永久属性成长、稀有度或刷取解锁。先把六项做成可信、可理解、值得选择的差异。

## 2. 当前实现盘点

### 2.1 分配、展示与存档

- `freshState()` 从 `TAL_KEYS` 中用 `Math.random()` 等概率抽取；当前六项，每项理论概率为 1/6。没有选天赋界面。
- `TALENTS` 有十二条名称和描述，`TAL_KEYS` 只有六条。两者职责混在同一文件，生效逻辑另外散落在调用处。
- 暂停菜单读取 `TALENTS[S.talent]` 的静态文案；没有显示免疫剩余次数、当前适用条件或最近触发记录。普通 HUD 不显示天赋。
- 存档分别保存 `talent` 和 `immuneUsed`，没有天赋规则版本。`Game.continue_()` 先执行 `freshState()`，再覆盖存档字段。
- 梦醒不会重新抽天赋，也不会主动补回已使用的免疫。当前已有保存后读档、药丸优先级、部分致命来源和分钟时钟的回归。

### 2.2 六项有效天赋

| ID / 名称 | 代码实际效果 | 适用范围与限制 | 玩家价值的主要问题 |
| --- | --- | --- | --- |
| `code` / 编程社 | 在网络中心没有 U 盘也可操作门禁终端 | 不绕过机房门锁，不代替行政楼同步及西小门三题验证；同房间货架可取得固定 U 盘 | 省一次搜寻和一个背包格；取得 U 盘后同一能力的边际价值很低，也不改变其他电子设备的操作 |
| `drive` / 车感好 | 没有车钥匙也可试车、启动正确车辆 | 仍需判断车辆、处理车库黑影并完成驾驶；无驾驶速度、转向或碰撞方面的专属效果 | 可能省去跨楼寻找车钥匙的行程，机会成本与同房间取 U 盘不同；名称与“搭线启动”也不完全对应 |
| `stomach` / 铁胃 | 食堂盛宴的累计停留惩罚阈值从 `>9` 延至 `>17` 个模拟运行秒 | 只影响 `feast`；不提高普通吃饭收益，也不改变药片、士力架或所有食堂危险 | 不遇到该异象便没有实际受益；原本及时离开的玩家很难感知多出的八秒 |
| `night` / 夜视 | 车库、夜间室外的区域额外 SAN 消耗乘 `0.55` | 不影响垃圾房、隧道、黑影近距离消耗、异象伤害或照退判定；没有专属渲染增亮 | 文案“暗的地方也看得清”与实现不一致，容易误导玩家以为可以不带手电 |
| `watch` / 秒表 | 无手表物品也能显示分钟时钟 | 与手表物品走同一个 `hasClock()`，普通与特殊时间段都不显示秒 | 实际更像不占背包的随身表；名称暗示秒级能力，取得手表后没有新增用途 |
| `immune` / 天生免疫 | 每局阻止一次进入 `kill()` 的致命结果 | 不知名药丸优先；救回时 SAN 至少 45、违规最多 40，并清理部分威胁；不会自动补回已消耗次数 | 覆盖面宽且额外恢复较多，与其他能力的收益跨度大；消耗后界面仍显示原来的静态承诺 |

区域消耗可以作量级对照，但不能据此推断实际存活时长：只计算该项消耗，车库每分钟从 33 降为 18.15 SAN，夜间室外从 18 降为 9.9；实际游玩还受怪物、异象、恢复与移动影响。当前没有足够的真人数据证明哪项最强或最弱。

### 2.3 六项旧档天赋

`map`、`hand`、`thin`、`cold`、`known`、`crowd` 不在新局池中，旧档仍可加载名称。不能把“还显示名称”当作“仍有能力”。

| 旧名称 | 重做前要解决的问题 |
| --- | --- |
| 过目不忘 | 全员已经有探索草图。若返场，应定义具体记忆差异，不能把基础地图从其他角色手里拿走 |
| 手稳 | 当前投掷不是一个已经成立的命中率玩法；不能为了让天赋有用，先给普通玩家增加随机失误 |
| 瘦小 | 调整体型会影响门、桌椅、柜子和碰撞可达性；垃圾桶已明确是死亡陷阱，不能恢复旧通路 |
| 血冷 | 容易与暗处适应、免疫和通用 SAN 减伤重叠，需要独立的行为取舍 |
| 熟人 | 需要足够的保安或校园人际交互支撑；一句额外对白不足以成为完整天赋 |
| 藏在人群里 | 需要真正存在的人群遮蔽与察觉规则，目前不能只凭描述重新放入随机池 |

上述六项作为兼容数据保留，本轮不安排全部返场。

## 3. 已确认缺陷与待验证判断

### 3.1 应先修复的确定问题

| 编号 | 问题及证据 | 影响 | 处理要求 |
| --- | --- | --- | --- |
| T-01 | `night` 只在 `dangerTick()` 改 SAN 倍率，描述却承诺能看清黑暗 | 错误准备和错误预期 | 首先把名称、短描述、详情、Wiki 对齐；不通过全局提亮来掩盖文案问题 |
| T-02 | 免疫用过后，暂停仍显示“总有一次要命的事会绕开我” | 玩家不能判断本局是否还受保护 | 明确显示“可用 1 次 / 已消耗”，继续游戏、梦醒和面板重新打开都一致 |
| T-03 | 没有正在运行的异象时，`immuneSave()` → `survivalReset()` 不保存；实测内存 `immuneUsed=true`、存档仍为 `false` | 消耗至下次存档之间退出或刷新，继续时会恢复未消耗状态 | 将一次性消耗、来源恢复与保存纳入同一结算；检查药丸同类路径。已有驾驶失败分支会额外保存，不能笼统说所有来源都漏存 |
| T-04 | `S.talent=d.talent||S.talent` 不校验 ID；未知 ID 可原样载入，缺字段则沿用读档前值 | 损坏或不完整档案行为不确定；继续前的随机初始化会参与兜底 | 统一校验与确定性迁移，不在读档时重抽 |
| T-05 | 暂停菜单仅在 ID 有定义时更新文本，不清空无效 ID 对应的旧文本 | 实测载入未知 ID 后仍显示上一次的“秒表” | 任何状态都产生完整的新视图；未知或旧版能力有明确说明 |
| T-06 | `drive` 无钥匙时，调查目标仍写“钥匙上的牌号可供核对”；试错文字仍可能写钥匙齿不对 | 路线提示与实际拥有的能力冲突 | 按开车方式与已发现证据生成目标、交互台词和失败记录 |
| T-07 | 产品文档 8.5 已列六项有效天赋，但 I-07 / Q-10 仍写移出五项、新局七项；8.5 时钟位置仍写右上 | 产品、代码和测试存在多个口径 | 统一现状表与验收条目，保留历史记录的时间范围；不要把新方案提前写成当前事实 |

T-03 是一个确认的消费落盘缺口，范围是“消耗后尚未再次存档”的窗口。不能推导为正常保存后也会补回免疫；现有保存后读档测试已经通过。本计划建议一次性保命立即提交，与本局只用一次的规则保持一致。

### 3.2 结构与体验缺口

| 编号 | 现状 | 判断边界 |
| --- | --- | --- |

## 4. 设计目标与边界

1. 开局能看懂“我擅长什么、什么时候有用、什么事仍然危险”，不需要先翻 Wiki。
2. 每项能力至少对应一种可主动采用的准备或行动策略；不要用大量泛化百分比填满空缺。
3. 任何普通逃脱路线都能在没有对应专属天赋时完成。路线必需信息、基础地图、基础可读性与输入容错继续属于所有玩家。
4. 规则与表现分开：调画质、亮度、字幕、暂停、打开调试面板都不改变能力强度或消耗次数。
5. 有效旧档保留已经获得的能力与用量；不通过更新静默补发免疫、重置冷却或改掉进行中的路线条件。
6. 保留既定分钟时钟、隐藏内容保密、药丸优先于天赋免疫、预知梦次数、课表、学生会检查、垃圾桶死亡和正常死亡删档规则。
7. 正常玩家不需要新增长按组合或多个技能快捷键。移动端通过现有交互按钮、手册和明确的上下文选项完成能力操作。
8. 本轮以单人游戏为交付目标；接口预留玩家状态参数，未来联机由权威端结算每人的天赋，不把共享世界状态变成个人能力的副本。

## 5. 推荐的产品方案

以下为本计划的推荐方向，尚未通过实现或试玩验证。先完成第 8 节 M0–M2，再逐项试做新效果；不一次性叠加全部增强。

### 5.1 新局选择

- 在难度选择后、正式初始化本局前，展示六项能力，另提供“随机一项”。六项数量不多，直接选择能避免为拿到某项能力反复重开。
- 每张卡片有一句角色描述、一条明确能力、一条限制和适用玩法标签。没有默认隐藏的惩罚，没有稀有度或强度排序。
- 确认后锁定本局能力。取消选择返回菜单，保留原存档；只有确认新局才开始替换旧局。进入选择界面不推进时钟、不触发异象、不占用鼠标锁。
- 随机入口使用同一有效能力清单，选择结果随本局保存；继续存档、梦醒和重建场景都不重抽。
- 选择前不展示未发现的具体路线答案、隐藏地点与触发时刻。可以写“适合电子设备调查”，不写解题答案和隐藏条件。
- 手机采用可滚动卡片列表、至少 44px 命中区；桌面支持 Tab / 方向键与确认。已选卡和确认按钮有独立状态，不能点击卡片即开始覆盖存档。

保留纯随机作为玩家可选方式。如果后续希望改为三选一，应单独比较决策负担与重开频率，不能将本方案同时做成两套默认流程。

### 5.2 六项能力的试做方向

| 能力 | 首先保留并说清的现有规则 | 推荐试做的差异 | 限制与验收重点 |
| --- | --- | --- | --- |
| 编程社 `code` | 不需要 U 盘；仍要进入网络中心并完成后续流程 | 每局第一次白名单错答可校验补救，免该次 SAN 损失；仍换题，仍须完成三次正确验证 | 不直接给正确答案、不免机房钥匙、不绕过同步；补救消耗随存档保存。若仍与 U 盘替代高度重叠，再评估终端玩法，不先新增大规模解谜 |
| 车感好 `drive` | 无钥匙也能尝试搭线；仍有错误车辆和车库威胁 | 把“免准备”变成“准备与风险的交换”：无钥匙搭线试验用 4.8 运行秒；有钥匙沿用 1.6 秒且优先用钥匙 | 操作可被走开/危险打断；不得绕过黑影、路牌和驾驶。暂不改最高车速、转向和碰撞范围，以免天赋承担基础手感修复 |
| 铁胃 `stomach` | 盛宴阈值保留 17 秒，对照普通 9 秒 | 普通 `eat` 活动恢复先试 +24 SAN，对照原 +18；沿用吃饭时间、冷却和 100 上限 | 只作用于普通吃饭，不作用于药片、士力架、盛宴奖励或所有“食物”文案；记录实际恢复量，满 SAN 不计为有效收益 |
| 暗处适应 `night` | 建议由“夜视”更名，保留车库和夜间室外区域额外消耗 ×0.55 | 首次进入适用区域给一次简短的适应反馈，详情列明正在生效的范围 | 不提亮世界，不透视，不减黑影近距离伤害，不免手电照退；保留 `night` ID 以兼容存档 |
| 守时 `watch` | 建议由“秒表”更名，保留无物品的分钟时钟 | 增加普通课表即将转换的简短提醒；持有手表时提醒仍有价值 | 候选提前量为按公开课表速率估算的 60 个运行秒，只显示文字，不显示秒或倒计时；不读取异象预报或隐藏时间窗，不重复学生会已有广播 |
| 天生免疫 `immune` | 保留每局一次、药丸优先；先不同时改 45 SAN / 40 违规的恢复边界 | 可用/已用状态、一次触发反馈、可靠存档，以及按致命来源完成恢复 | 不补发第二次，不从梦醒或调试预览恢复次数；对场景持续危险的处理必须有来源级验证，不用“全场永久无敌”兜底 |

上述 4.8 秒、+24 SAN、60 秒提醒及编程社的一次补救均是**试验值/试验机制**。旧局先沿用旧规则；新规则版本只用于明确开始的新局。试验结果不足时保留结构与可靠性改进，回退相应效果配置。

“守时”的提醒规则还须明确：每个普通课表边界每天最多提醒一次；暂停/后台不推进；时间跳过不补播已过期提醒；跨日更新日期键。对临近边界的短时段最多发一次，不连播多条。提醒不改变课表、不自动请假、不展示下一次异象。

### 5.3 反馈与信息位置

- **暂停**：名称、明确效果、限制、可用状态/次数。旧版能力、未知数据和已消耗能力都有完整文案。
- **手册**：增加本局能力说明入口与少量最近生效记录；已发现路线可引用对应能力，未发现路线只给泛化适用说明。
- **上下文交互**：使用“搭线启动”“插入 U 盘”“直接操作终端”等与实际来源一致的动作文本；同时有物品与天赋时解释采用哪种方式。
- **生效反馈**：首次进入适用区域、一次性触发或明确交互结束时短暂提示；不逐帧刷字，不增加常驻 SAN 数字或秒表倒计时。
- **调试**：可查看效果配置、状态、来源和最近事件；更换测试天赋明确重置或保留状态，不悄悄写入正式存档。预览只读正式玩家状态。

## 6. 技术结构

### 6.1 一个定义源，有限的能力接口

新增 `game3d/js/talents.js`，保留稳定 ID，将名称、短描述、限制、选择资格、规则版本和配置集中管理。旧版六项显式标记为不可新选，清单由定义生成；不要另维护一份易漂移的可选 ID 表。

推荐接口职责：

| 接口方向 | 调用者 | 要求 |
| --- | --- | --- |
| `definition(id)` / `view(player)` | 选择、暂停、手册、调试 | 纯读；非法 ID 也返回安全、可显示的结果 |
| `capability(player, context)` | 终端、车门、调查提示 | 同一返回值提供是否可用、采用的方式及限制，避免提示与判定各写一份 |
| `modifier(player, source)` | 区域 SAN、盛宴、吃饭 | 明确来源，例如 `danger.garage`、`anomaly.feast`、`activity.eat`；无匹配返回中性值 |
| `tryPreventDeath(player, context)` | 既有死亡结算 | 返回是否救回及消耗来源；不自行操作场景、生成模型或保存半完成的状态 |
| `onPublicSchedule(...)` | 课表更新 | 仅使用普通公开课表，处理提醒去重与过期 |
| `normalizeSaved(...)` / `serialize(...)` | `SAVE_SCHEMA` | 版本迁移、字段裁剪和明确的兜底策略 |

不引入任意字符串触发的大型事件总线。先覆盖现有六项需要的少量接口；纯规则不依赖 Three.js、DOM 或浏览器时间。消费者可使用旧函数适配一轮，但最终应删除散落的 `S.talent==='…'` 判定，包括调查文案中的分支。

### 6.2 状态归属

保留 `S.talent` 为当前 ID，新增一个天赋状态对象，避免到处添加 `xxxUsed`：

```js
talent: 'immune',
talentState: {
  schemaVersion: 1,
  rulesVersion: 1,
  origin: 'selected',
  consumed: { fatalProtection: true },
  counters: {},
  notified: {}
}
```

此结构为提案。`talentState` 不再复制 ID，运行时以 `S.talent` 为唯一 ID 来源；定义决定允许的键及取值，不能把任意存档对象直接并入状态。

建议规则版本 1 表示本计划核对的现有六项效果，后续试验使用新的规则版本；存档结构版本与效果版本分别演进。修文案和补状态展示本身不改变旧局的效果版本。

- 每局次数、补救记录和提醒去重键随存档走；固定上限和倍率属于版本化定义。
- 如后续引入冷却，使用既有模拟运行时间/游戏日历的明确一种，不使用后台照走的 `Date.now()`。
- 渲染高亮、提示淡出等纯表现状态不写入能力状态。
- `immuneUsed` 在迁移入口转换为 `consumed.fatalProtection`；兼容期如仍写旧字段，应从新状态派生，不能保留两个可独立修改的权威值。

### 6.3 致命结果与保存的结算边界

保留现有顺序：已经死亡的重复调用不再处理；调试无敌不消耗资源；正常保护先药丸、后天赋免疫，未挡住再执行死亡或预知梦。

一次救回按下列顺序结束：

1. 根据致命来源和事件标识判断是否已结算。
2. 选择保护来源，在内存中消耗一次。
3. 执行共有恢复，再由来源完成自身恢复：例如同化回落、驾驶检查点和威胁结束。已经存在的来源处理要复用，不重复做一遍。
4. 状态稳定后保存完整快照，最后发送反馈与本地试玩事件。

不能只在 `immuneSave()` 里插入 `autoSave()`：该时点驾驶检查点、同化回落等调用方后续工作可能尚未完成，会留下另一种不一致存档。应让外层结算拿到结构化结果，统一在来源恢复结束后提交。

保存失败时保持内存中的消耗结果，提示“本次变化尚未保存”，提供重试并保留失败诊断；不假称已保存，不退还能力以便再次触发。单机本地存储无法防止用户主动编辑或恢复旧文件，本轮目标是修复正常操作下的遗漏，不承诺反作弊。

## 7. 兼容与迁移

| 输入情况 | 推荐迁移行为 | 禁止行为 |
| --- | --- | --- |
| 当前六项有效 ID + 有效旧字段 | 保留 ID；按旧规则版本运行；转换已用次数 | 自动升级成更强能力并补次数 |
| 六项已退役 ID | 保留原名，标注旧版特性目前无额外作用；在安全的暂停状态提供一次可选转换，确认后保存 | 静默替换、把旧名称继续当有效承诺 |
| 缺失或未知 ID | 确定性转为内部中性 `none`，显示可理解的修复提示；允许一次明确选择 | 沿用新局随机结果，或显示上局名称 |
| 已经消耗免疫的旧数据 | 保留消耗事实；如果转换为免疫，不能补回该次保护 | 借迁移/转换反复获得保命 |
| 新状态缺字段或字段异常 | 按该版本定义补缺、裁剪非法值，记录兼容原因 | 负次数、无限冷却、未知效果直接进入运行时 |
| 未识别的新规则版本 | 保留原始存档备份，给出版本不兼容说明，不覆盖源档 | 以默认版本继续并自动覆盖，造成不可逆信息丢失 |

可选转换只服务兼容，不成为正常局内洗天赋入口：不处于异象、巡察锁定、检查、电梯、驾驶、死亡或未完成选择中；转换标记持久化且重复进入不再给予机会。没有选择也可以保留原档继续。上线前补一份原始存档备份，确认迁移后的完整快照写入成功再使用新格式。

更改新局能力选择不应重置成就、已发现结局、死亡提示记录、画质和输入设置。梦醒、读档、切画质、进入房间分别列为生命周期测试入口，不能共用“重新抽取并初始化”的函数。

### 9.2 正常操作与平衡记录

扩展现有自愿开启的 `Playtest`，仍仅本地保存/导出。记录天赋 ID、规则版本、选择方式、难度、路线、首次看说明、机会数、生效数、有效收益、消耗与失败来源；不在每帧写一条事件。

区分三种量：

- **有机会**：到了可用场景。例如进入普通吃饭活动、无 U 盘操作终端、进入车库危险区。
- **生效**：能力确实改了结果。例如免去一次物品要求、延长盛宴宽限、免去一次致命结果。
- **有效收益**：给玩家增加了什么。例如实际恢复/少损的 SAN、节省的背包占用、改变的准备行程。满 SAN 的额外恢复、已经有钥匙的免钥匙能力不能算完整收益。

按难度、路线、玩家熟悉度拆分比较，避免把熟练玩家偏爱的路线误认作天赋强度。对照局尽量固定世界与事件条件；天赋选择用独立随机源或直接指定，不通过改写全局 `Math.random()` 改变整局掉落。规则推演可以固定事件，真人试玩要另外标明。

验收建议：

1. 首轮邀请至少 6 名未读内部攻略的玩家，记录选择理由；至少 5 人能复述所选能力的主要作用和一条限制。样本用于发现问题，不宣称统计意义上的平衡。
2. 每项至少做 3 段正常操作的相关情境记录，并记录没有遇到相关情境的完整局。不能只安排一定能触发的片段来证明价值。
3. 车辆路线分别用 `drive` 和非 `drive`，白名单分别用 `code` 和非 `code`，完成正常准备/操作流程；传送门没有专属天赋，选至少两项不同生存能力验证。布置条件后的终点测试与自然收集通关分列。
4. 不要求选择率平均分配；若某项反复因“不知道有什么用”“拿到普通物品就没有差别”被放弃，回到设计调整。若某项跨路线都被选作唯一合理答案，检查收益和代价。
5. 在安卓、iOS 或可获得的实际设备上记录选卡、详情、提醒和存档恢复，不用桌面触屏模拟替代真机结论。
