## 2. P0：传送门实体建模全面重做

### 2.1 目标效果

把当前以简单圆环、平面光盘、材料小球表现的装置，重做为**能被玩家从不同角度观察、能与实验室环境互动、能在成形过程中表现实体结构的完整 3D 传送门**。整体风格应符合校园物理实验室：由旧实验设备、金属支架、铜线圈、透镜、荧光试剂与供电部件临时组装，不变成凭空出现的科幻魔法门。

建议分为五个视觉层级：

1. **实体基座**：置于实验台上的金属框架、支撑脚、固定栓、固定角件、线缆和供电接口，带真实厚度与接触阴影；未组装时也能看见基座。
2. **材料组件**：铜线圈具有可辨识绕线与导电路径；透镜有厚度、折射或可承受的近似表现；试剂瓶有液面、冷光和玻璃质感；电池有插槽与导线连接；四种材料与已有收集规则一一对应，不能凭空省略某项。
3. **成形环结构**：多层不同半径的刚性环、隔开的固定件与能量导轨，显示组装过程中逐段闭合、校准和充能，而不是一片悬浮发光的 2D 圆盘。
4. **门内空间**：用多层深度、波纹、视差、流光与低频扭曲模拟稳定的空间裂隙；门内有明显“通往另一侧”的视觉深度，不用高亮纯白平面长期替代；角色靠近时可有轻微响应。
5. **动态细节**：通电后局部亮起、线圈脉冲、试剂逐渐发光、环体轻微振动、粒子与音效同步；画面不能频闪致眩或过曝遮挡视线。

### 2.2 建模与场景集成

- [ ] 先检查 `game3d/js/model/room.js`、`model/kit.js`、`model/materials.js`、`game3d/js/portal.js` 和 `game3d/js/cutscene.js` 中已有实验台及演出模型；建立尺寸、局部坐标、玩家视高与碰撞边界的基线，不重造已有材料拾取系统。
- [ ] 设计独立的可复用传送门模型／组件生成器（例如 `game3d/js/model/portal.js`，实际文件名可按项目结构调整），明确**未组装、可组装、充能、开启、进入、关闭**各阶段的对象显示与动画状态。
- [ ] 让探索阶段模型、实验台交互后的常驻门和结局过场**共用同一套外观配置及部件**；可以让 CG 创建独立实例，但不能变成“平时一张图，过场另一套门”。
- [ ] 模型与实验台／附近家具的碰撞、遮挡、第一人称镜头、可操作距离一致；门后缘、支撑梁不能挡住必经路线，玩家不能卡进模型、从环体走穿到墙里。
- [ ] 模型的运动、光照、粒子、音量与交互进度由状态和时间轴驱动；暂停、读档、离开场景、切画质和 CG 跳过都能恢复正确阶段。
- [ ] 五档画质使用分级几何与材质：低画质保留一眼认得出的圆环与实体厚度；高档增加线圈、倒角、材质反射和高质量光效。最低档不依赖昂贵的折射或大面积透明排序，所有档位的实际交互判定保持相同。
- [ ] 核对模型包、材质缓存、几何共享、异步加载、首帧着色器预热和释放时机，避免反复进入实验室或重看 CG 时显存增长与卡顿。
- [ ] 对比组装前／后／激活时／进入时，固定机位、斜侧面与第一人称近距离截图；按项目规则做穿模检查和性能基准，确认阴影、透明遮挡、光照与物理尺度正确。

### 2.3 严格保留的玩法

- 保持既有隧道、日记、图纸、材料、实验台条件与失败／重试语义；本次重做重点是**建模与演出衔接**，不是取消原先探索过程。
- 只有真实完成装配并满足既有条件才出现可进入的门；只做 CG 预览或调试传送不能得到材料、结局或存档奖励。
- 开启后读档仍有正确模型与可交互入口；未开启时不能被视觉漏洞误判成已经能通过。
- 白光转场仅在真正进入后触发，支持镜头晃动／闪光弱化选项；跳过仅跳过演出，不跳过必要玩法。

**P0 验收**：真实探索完成图纸和材料后，模型按阶段建立；五档画质均可正确显示和交互；与实验台无穿模；离开、读档、跳 CG、重复进入无残留和重复生成；桌面和安卓低画质均能辨认门的结构（真机未测不得写通过）。

## 3. P1：死亡 CG 档案室——每种死法解锁一个

### 3.1 产品规则

玩家在主菜单进入 **“死亡 CG 档案室”**，查看已解锁的独立死亡条目；未经历的死法保持锁定，锁定项不展示 CG、死因答案或特殊触发步骤。

**唯一核心规则：同一种真实死亡原因首次发生时，永久解锁与该死法对应的一个档案；同一种死法再次发生不重复增加解锁数，不同死法分别解锁自己的条目。** 解锁仅表示玩家确实经历过死亡，不代表获得结局、奖励或高分。

- “一种死法”的稳定主键应以**实际死亡原因类别**为准，先核对 `kill(msg,fx,source)` 的所有调用：当前调试面板 30 种 `fx` 是起点，不应未经审计就把 30 当作最终档案总数。
- 同一语义死因若仅由于不同 NPC 或场景复用同一 CG，应避免制造两个毫无区别的档案；不同真实死因若意外复用 `fx`，要明确是否分别建档并为各自匹配代表演出。建立**死因 ID → CG 资源 ID → 展示名称 → 解锁条件 → 测试**的内部注册表，具有稳定 ID 和迁移映射。
- 玩家经历的**真实致死事件**通过 `kill()` 的保命拦截后，首次进入真实死亡分支时解锁；如果第一天“预知梦”死亡后惊醒，仍算已经真实经历了一次死亡，可解锁；药丸／免疫／调试无敌拦截的“没有死”**不能解锁**。
- 调试预览、`Dev.death()`、CG 回放、强制播放、测试注入、加载死亡记录或单独触发死亡画面不得当作玩家正常死亡而授予新档案。实施时应使用明确的死亡上下文来源标记，不能只根据 `S.dead` 或 `deathFX()` 是否运行判断。
- 成功解锁后跨局永久保留，不因正常死亡删档、通关清档、新开存档或切换画质而丢失；同设备浏览器本地存储清空后记录可能丢失，需明确提示。
- 不向公开 Wiki 暴露彩蛋死法、彩蛋异常、隐藏触发时刻。包含秘密的档案只在玩家**亲身实际解锁后**显示；锁定列表采用问号／密封档案，不展示可以推断总数量、名称、触发条件的线索（是否展示一般公开死法总数可另定）。

### 3.2 玩家可见交互与 CG 回放

- 主菜单增加独立入口“死亡档案室”，进入后显示已解锁、尚锁定与最近解锁；单个档案包含内部编排的标题、死因简述、首次解锁（可选）、重看 CG 按钮。
- 档案页、详情页、确认重播均保留现有菜单恐怖氛围；手机触屏可以滚动、点选、返回，PC 支持键鼠、Esc 与焦点管理。
- CG 以**不影响正在进行游戏的隔离预览状态**播放：从固定可复现的安全舞台／指定示范场景播放该类型真实 CG，调用已有 `DeathCG`、`DeathTimeline` 或适配的预览接口。不得触发 `kill()`、`endMark()`、`saveGame()` 或永久剧情状态更改。
- 可重复回放、跳过、重播、返回档案列表；播放中切菜单、触屏退出、画质切换、窗口失焦、资源加载失败均要安全停止并释放资源。
- 锁定内容只显示统一“尚未记录”反馈；解锁瞬间可选地显示一行简短提示，不能让本来紧张的死亡过程被奖励弹窗打断。建议在死亡 CG 或结算卡结束后提示，而非在致死瞬间弹出。
- 无音频或弱化闪光时仍可观看；回放以现有 CG 为主，不为了档案室复制 30 份预渲染视频或引入大量下载体积。

### 3.3 数据模型、历史迁移与公平性

- 建议建立独立的带版本存储（如 `wdfz3d_death_archive_v1`），核心字段：`version`、`unlocked{deathId:true}`、可选 `firstSeen`；不存储 CG 图片／视频，不在存档里放大段媒体资源。
- 参考现有 `wdfz3d_deaths` 的 `counts/sources/last` 做**历史记录迁移评估**。旧日志仅记录 `fx/source` 和次数，未记录是否来自调试：不能毫无审计地把所有历史计数认作真实自然解锁。建议有来源证明的记录可迁入；来源不明的旧记录标记“历史待核验”或继续锁定，具体迁移政策实施时确定。
- 数据损坏、异常类型、未来新增死法、重命名死法、重复执行迁移、存储配额失败都必须安全降级。不同游戏版本的旧档案 ID 不得被错误改成另一种死法。
- 档案解锁只更新档案专用记录，不覆盖 `ENDS_KEY`、游戏进度或现有死亡学习提示；本地记录不代表联网账号同步。

### 3.4 必测场景

- [ ] 遍历所有可达真实死法：首次解锁一个、同类重复不增加、不同死法各增加一个；已解锁 CG 与死因匹配。
- [ ] 药丸／免疫／无敌／调试预览／档案回放不误解锁；“预知梦”真正死亡后惊醒可解锁且不提前删除跨局档案。
- [ ] 旧版 `wdfz3d_deaths` 迁移、损坏 JSON、未知 ID、重复迁移、刷新浏览器、本地清空；解锁与结局历史互不影响。
- [ ] 快速连续进出／跳过回放、安卓触屏、PC、五档画质、声音／晃动开关、资源创建释放和主菜单恢复。
- [ ] 未解锁档案在界面、DOM、页面 SEO、公开 Wiki 以及只加载必要的玩家可见数据中都不能直接泄露隐藏内容。

**P1 验收**：所有经审计的真实死因“一种解锁一个”；重复只记经历次数不增加解锁数；回看可运行、可退出、无副作用且不会泄漏未发现的隐藏秘密。

## 4. P2：速通模式——独立计时通关与本地成绩

### 4.1 模式入口与基本玩法

- 在主菜单增加 **“速通模式”**。可选择现有“预知梦／梦魇”难度的对应速通挑战，按原有地图、路线、道具、事件、怪物、智力挑战与死亡规则完成逃脱；**速通不应默认移除剧情挑战或赠送道具**。
- 普通模式保持原样，新增模式有独立的标识与存档／成绩，不篡改既有继续游戏存档。建议首版只做单人本地挑战，不承诺联网排行榜或防作弊认证。
- 在画面固定角显示计时器（例如 `00:08:32.45`），可以在设置中隐藏但后台继续计时；不遮挡 SAN 身体反馈、字幕、地图和触屏操作。通关后出现本次时间、个人最好、路线与难度、是否有效的成绩卡。
- 速通路线以普通**已确认的真结局**为有效通关目标（目前包含开车、白名单、传送门）；必须完成原本真正可操作的驾驶、挑战和装置组装过程。其他死亡／失败分支计作失败；隐藏成功路线是否单独作为**秘密分类成绩**，只在玩家已亲自发现后在内部结算展示，不能事先公开路线名称和触发方法。

### 4.2 计时口径（推荐默认，实施时明确配置）

为了避免“游戏时钟加速、剧情跳时和帧率不同导致伪速通”，用**真实经过时间**而不是 `S.tsec` 作为核心成绩口径：

| 时点／情境 | 建议规则 |
| --- | --- |
| 起点 | 从新局完成必要加载、玩家**首次真正获得可操作控制权**时开始；前情提要与不可控载入不计。是否允许跳过序章，须对同一成绩分类保持一致 |
| 正常探索、走路、解谜、驾驶 | 全程计时；优先基于单调时钟（如 `performance.now()`），不依赖 `requestAnimationFrame` 累计帧数 |
| 菜单暂停、打开背包、剧情 CG | 推荐 **RTA 实时时间继续计时**，防止靠无限暂停研究路线得到不真实的成绩；同时可提供辅助 IGT（不计已规定的非操作时间），但不能与 RTA 混合排行 |
| 切标签页、手机切后台、长帧、系统休眠 | RTA 不得因为渲染暂停而无故停表；恢复后核对真实经过时间，记录异常与可能失效原因；不能靠刷新／卡后台缩短计时 |
| 终点 | 在 `triggerEnding()` 或对应路线的**最终真实通关条件被确认且不可撤销**之时停止；不等待可跳过的结局 CG 播放完或玩家点结局卡，因此跳 CG 不影响成绩 |
| 死亡、放弃、回主菜单 | 结束本次挑战并标记“未通关”，不写为个人最佳；“预知梦”可复活机制按已选难度现有规则继续，但整次计时**不重置** |
| 读档／刷新 | 推荐首版**严格速通不允许通过读取旧存档接续刷有效成绩**：载入后标注练习／无效计时，避免倒带刷时间；如未来提供可续跑的休闲计时，必须和严格成绩分开 |

以上是可落地的**默认设计建议**，不是用户已逐项确认的赛事规则；若要定义独立的竞技榜单或上传功能，应另行确认计时类型、暂停与断线政策。

### 4.3 成绩数据和防误计

- [ ] 明确 `Speedrun` 独立状态机：`idle → ready → running → finished/failed/abandoned/invalid`；新局只允许生成一个 runId，重复触发结局、连点完成、跳过 CG 不得重复结算。
- [ ] 保留 `mode`、`difficulty`、`routeId`、`elapsedMs`、`runId`、`status`、`invalidReason`、`rulesVersion`、`gameVersion` 等字段；如统计中途分段计时，里程碑仅以真实达成的剧情节点写一次。
- [ ] 独立存储最近记录、各难度与各**已公开普通路线**的最佳纪录；隐藏路线记录仅在真正发现后显示，不把所有结局数量暴露在主菜单。
- [ ] 使用单调时钟计算当前会话高精度耗时，并有可靠的刷新／失焦处理；页面重新打开后不能从旧运行时毫秒时间戳拼出负数或虚假短时间。
- [ ] 明确调试面板、传送、无敌、注入物品、直接调用 `triggerEnding(id)`、人为修改本地数据等情况下成绩无效；浏览器本地成绩**只能做个人参考，不能声称具有服务器反作弊能力**。
- [ ] 速通成绩、解锁档案、普通结局、存档进度四类状态分别持久化，避免某项清档删除其他记录；`Game.start()`、`Game.continue_()`、`Game.quit()`、`saveGame()` 与 `showEndingCard()` 接入需逐一核对。
- [ ] 本地纪录按玩法规则版本分组，规则变更导致路线时长明显不同则不跨版本强行比较；旧记录保留可查与适当版本标识。
- [ ] 玩家可以查看自己的成绩、最好时间及失败原因；公开 Wiki 可以解释“速通计时模式的一般操作和公开路线”，但不得列出任何未公开的彩蛋信息。

### 4.4 测试矩阵

- [ ] 起点和终点精确落在可操作／判定时刻，不受过场长度、渲染帧率、跳过 CG 和游戏时间快慢影响。
- [ ] 两种难度、三条公开普通逃脱路线各自完成一次，核对路线真实挑战、时长与 PB 独立。
- [ ] 暂停、打开菜单、前后台切换、长帧与系统休眠后计时仍正确；切后台不会反向减少或重置时间。
- [ ] 死亡保护和醒来、普通死亡、放弃、再次开始、快速连点结束、重复触发结局、调试运行都不能创造虚假 PB。
- [ ] 旧存档升级、坏成绩数据、本地存储不可用、清理普通进度／清理记录；成绩界面在安卓触屏小屏与 PC 上不遮挡操作。
- [ ] 新版本规则变更、隐藏秘密保护、无联网时仍可使用个人本地成绩功能。

**P2 验收**：普通模式不受影响；速通新局从真实可操作点起计，到最终真实完成点停表；能在本地查看按难度／路线分类的成绩；伪通关／调试无法生成有效纪录；对边界有自动化测试。

## 5. P3：进入游戏时的 3D 启动 CG（开场过场）

### 5.1 需求与现状

**新增用户需求：在点击“开始游戏”进入新一局时，先播放完整的游戏启动 CG，然后自然交接给玩家控制。** 这是一段真正的 3D 镜头与环境演出，不是仅在网页加载时播放 Logo、简单视频封面或文字页。

现有 `game3d/js/prologue.js` 已提供 `PRO_PAGES` 文字式前情提要、`proShow/proNext/proEnd`、闭眼睁眼的 `eyelid/proWake` 和“正常世界变成里世界”的切换；`game3d/js/main.js` 的 `Game.start()` 根据 `proSeen()` 首次显示前情提要，老玩家直接进入。**应基于现有前情逻辑升级**，保留必要叙事和状态，不创建冲突的第二套开场流程。

### 5.2 电影式分镜（建议艺术方案）

1. **正常的第四节课**：镜头缓缓掠过有阳光的校园与高二教室，老师讲课、同学翻书、粉笔灰飘落，色彩与环境声自然。
2. **细微不对劲**：老师重复一句话，墙上时钟出现异常，学生动作逐渐不自然，远处出现短促的电流声；以音效和镜头停顿而非大字提示制造悬念。
3. **时间停滞**：粉笔灰停在半空、钟声失去尾音、日光逐渐冷却，镜头从旁观视角转向主角座位，空间中的人物变得静止。
4. **坠入里世界**：灯光不稳定、色彩缓慢褪去、远处走廊的轮廓显得异常；配合短暂闭眼黑场、呼吸声和低频音效，不能过曝或用无意义频闪。
5. **第一人称醒来**：镜头从课桌抬起，看到教室里坐满了人却无人回应；保留现有前情提要的关键剧情信息，最后镜头位置、视角、座位状态与实际可操作开局完全一致。
6. **控制权交接**：HUD、触屏摇杆／键鼠输入和环境声音按时间轴自然接管，明确只在此刻解除过场锁定。CG 不应提前触发怪物追击、资源消耗或计时。

以上是建议分镜，不在开场中暴露未发现的隐藏路线、异常触发时刻、秘密结局或解决方法；细节可在实施阶段调整。

### 5.3 功能、性能与兼容

- [ ] 建立可维护的 `OpeningCG` 或类似时间轴，明确 `loading → opening → handoff → playable` 状态；沿用 `prologue.js` 已有文字、世界切换和睁眼逻辑，避免重复弹出旧文字前情提要。
- [ ] 以现有 3D 教室、学生、课桌和环境为基础制作镜头运动、人物定格、光照变化、粒子与空间音效；能在五档画质运行，低画质保留叙事关键动作。
- [ ] **首次开始新游戏**默认完整播放；老玩家新开局可选跳过／简短版／重看完整版，具体按钮行为应与 `proSeen()` 的现有逻辑协调。继续存档不重复播放开场；回到主菜单后允许从独立入口重看（可选）。
- [ ] 开场任何时刻都可明确跳过（PC 键盘／鼠标与安卓触屏）；跳过必须一次性、幂等地完成必要的世界状态、角色位置、镜头、音频和 HUD 交接，不能因为跳过时刻不同造成存档、剧情或开局位置差异。
- [ ] 开场播放时屏蔽正常移动、交互、怪物 AI、体力／理智消耗、剧情随机触发和手动存档；必要的渲染与镜头更新可继续。演出结束才恢复可操作。
- [ ] **速通计时在开场 CG 完成或跳过、真正获得操作权时开始**；过场、加载与不可操作转场不计入成绩；无论完整观看还是跳过都从同一可操作开局状态开始，保证同类别成绩可比。
- [ ] 音效可关闭、字幕可读、镜头晃动／闪光弱化选项生效；画面与镜头不能造成长时间眩晕或过度闪烁。
- [ ] 处理资源加载失败、快速连续点击跳过、后台切换、浏览器音频自动播放限制、切换画质、重复进入游戏、意外退出 CG；不应白屏、卡输入、留残影或残留音频。
- [ ] 检查模型和着色器预热、首次进入延迟、低端安卓性能与显存释放；尽量复用 `prologue.js`、`cutscene.js` 和现有场景，不强制下载巨型视频资源。

### 5.4 验收测试

- [ ] 首次新局完整 CG → 自然交接；老玩家新局跳过／重看；继续存档不触发开场。
- [ ] 在每个关键分镜点执行跳过，最终 `S.room`、坐标、朝向、`VisualState.worldNorm`、剧情标志与正常播完一致；无重复回调或悬挂定时器。
- [ ] 演出中无死亡、无道具／体力／理智消耗、无提前自由移动；结束后 PC 与安卓触屏立即可正常操作。
- [ ] 速通完整观看和跳过 CG 的起跑状态相同，计时都从首次获得操作权开始；画质、声音、弱化闪光、后台恢复无异常。
- [ ] 对比开场截图与分镜，检查摄像机穿模、人物动作与课桌遮挡、黑场切换、灯光及颜色连续性；对五档画质、桌面浏览器和安卓真机分别验证。

**P3 验收**：进入新游戏时有完整的电影式开场 CG，能跳过且不破坏原有剧情和存档；交接自然、镜头不穿模；速通模式不因观看开场时间不同而改变有效成绩。

## 6. 集成与代码边界

建议按现有职责逐层接入，避免把所有实现堆在一个脚本里：

| 职责 | 现有参考文件 | 计划工作 |
| --- | --- | --- |
| 传送门建模 | `game3d/js/model/room.js`、`model/kit.js`、`portal.js`、`cutscene.js` | 建立实体组件、场景表现和状态一致的 CG 复用 |
| 死亡档案注册与解锁 | `story.js` 的 `kill/deathLogAdd`、`fx/death-cg.js`、`fx/death-timeline.js`、`dev.js` | 统一死因 ID、可信解锁入口、独立持久化及回放预览 |

| 主菜单与 UI | `index.html`、`game3d/js/main.js`、`game3d/js/ui.js` | 增加“死亡档案室”和“速通模式”入口，保持现有菜单与触屏风格 |

- 功能分开落地，但共享仓库统一的状态、资源释放、输入恢复和错误反馈约定；日志和存储字段不泄漏隐藏路线的公开文本。
- 在菜单／档案 CG 回放模式与实战模式之间建立严格资源隔离；回放不会触发巡察者、异象、结局、死亡日志或速通成绩。
- 所有 UI 新功能应具有明确加载失败、数据损坏、无可用记录时的提示及恢复方式，不能让未加载完资产的按钮造成白屏。

- [ ] **M2 死亡档案室**：完成稳定死因 ID、可信首次解锁、跨局保存、锁定保护、独立 CG 回放、历史日志迁移策略及防调试误解锁回归。

### 未决而非擅自定案的产品细节

1. 传送门的最终外观偏向“旧式校园实验设备改造”还是更强烈的超自然异界裂隙？本文给出可实现的参考外观，最终美术方案待制作时对照参考素材确认。
2. 旧死亡日志是否追溯解锁旧版本的档案？应先明确哪些来源具有可信度；默认不把来源不明的调试记录当作正常解锁。
3. 速通赛制主计时是否采用推荐的 RTA（暂停持续计时）、是否另显示 IGT、是否允许练习续跑？默认首版采用保守的本地 RTA 建议，不宣称竞技官方标准。
4. 是否允许隐藏成功路线参与个人 PB？如有，必须仅对已经实际发现的玩家显示，不能通过排行类别暴露秘密。
5. 是否要未来增加云同步／全球排行榜？**不属于本次最低交付**；本计划先完成稳定的本地单机功能。

**完成标准**：四项功能真实代码交付、对应自动化和适用实机验收通过，状态、文档、截图与公开 Wiki 保密检查齐全，才能将目录状态记为“已完成”。只完成其中若干项时应标为“部分完成”，保留本文原文件名并标明剩余工作。
